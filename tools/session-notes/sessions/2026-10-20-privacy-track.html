Highlights

1How PayJoin v2 works

The hard part is not the transaction, it’s the conversation. In a PayJoin, the receiver adds one of their own coins to your payment, so the sender and receiver have to swap a partly signed transaction (a PSBT) before it is sent. In v1 the receiver had to run a web server that was always online. Version 2 moves that job to two shared servers that anyone can run.

The reply goes back the same way. The receiver can be offline when you pay. Their wallet picks up the mailbox later, and the payment finishes then.

Everything is in the PayJoin link. A v2 receive link looks like a normal Bitcoin address with a long tail. That tail carries three things:

Inside a PayJoin v2 link

directoryWhich mailbox server to use mailbox IDLike an email address for this one payment public keyThe receiver’s key. The sender uses it to encrypt the PSBT, so the directory only sees a locked blob

What do you have to trust? Very little. The servers never touch bitcoin and can’t read the payment. The directory could still see which IP addresses use the same mailbox, so the relay sits in front of it, a bit like Tor. If one company ran both the relay and the directory, it could link the IPs again, so they should be run by different people. You can see which ones your wallet uses under PayJoin in the advanced settings of Cake Wallet or Bull Bitcoin.

2Testing it live

The protocol works. The wallets don’t, yet. One incoming PayJoin from an earlier session showed up on mempool.space as 2 inputs and 2 outputs, exactly as it should. Then we tried to send more on the call, and almost every attempt hit a different wall:

What we ran into

Silent fallbackCake Wallet to Cake Wallet sent a normal payment. Cake quietly falls back when a PayJoin fails, and doesn’t say so.
Paste vs scanPasting the link failed with an address error. Scanning the QR code worked.
Version mismatchBull Bitcoin showed a “v1” error. Sender and receiver need the same version.
Empty or unconfirmedThe receiver needs confirmed coins of their own. An empty wallet can’t join, and unconfirmed coins gave “confirmation failed”.

Also: Bull Bitcoin asked for a minimum of about 10,000 sats, which isn’t in the PayJoin spec, and some wallets just spin with no error at all.

“Show me the error. Show me what I can do. Tell me if it worked.”

Key takeaways

Use it every time, not once in a while. PayJoin looks like any normal payment, unlike a CoinJoin, which is easy to spot and often gets flagged. The idea shared on the call: if even 5 to 10% of payments were PayJoins, chain analysis could no longer trust its “all inputs belong to one person” guess for any payment.

Know the trade-off. The person who receives your PayJoin learns a little about your coins, and you about theirs. It’s similar to what happens when you combine coins in one transaction anyway.

Where to start contributing. Build and run rust-payjoin first. Make a PayJoin, break a test. Then pick one of the open pull requests and review it. It can take days, and feeling lost is normal. Bindings for other languages and the new BTCPay Server plugin both need help, and the wallet issues from the live test are worth reporting.

Inputs in a PayJoin?At least two. More is allowed in theory, but wallets use two today.
Is v2 more private than v1?Yes, thanks to the relay and the directory.
Who can host the relay?Anyone.
What does the directory see?Only the receiver’s public key, not the PSBT or your IP.
Who needs to read the UTXO set?Only the receiver. The relay and directory need no Bitcoin node.
