Highlights

1FIPS with Alex

An internet where your address is a key you make yourself. Today, to reach anyone online you need an IP address from your internet provider and a domain from a registry. Both are handed out from the top down, both can tell where you are, and both can be switched off. FIPS, the Free Internetworking Peering System, swaps them for something Bitcoiners already know: every node makes its own key pair, and its Nostr npub is its address. Nodes find each other and route messages through a self-organizing mesh, with no central server in the middle.

Alex met the creator, Jonathan, in Madeira, where Nostr developers had FIPS apps talking over Bluetooth.

Mini-game 1 · Mesh Maker✓ badge earned

Knock out a node. Who gets cut off?

A question from the call: what is the difference between decentralized and distributed? Pick a shape, then tap any node to take it offline. Try all three shapes to earn the badge.

Tap the big node in the middle first.

The answer the group landed on: in a decentralized network there are clusters, and each cluster hangs off a head node, so between two nodes there is often only one route. Lose a cluster head and a whole branch goes dark. In a distributed network every node has several ways to reach every other node, so one crash barely matters. FIPS is the distributed kind. It has no hierarchy at all: nodes compare addresses to build a spanning tree and pick a good path.

The clever part: FIPS only replaces the addressing layer, so apps that speak IP can run on the mesh without changing anything. Moving a server onto FIPS should not need a rewrite.

Why not just use a VPN? A VPN only hops your traffic through another company’s servers. Those servers sit on a known family of IP addresses, so they are easy to spot and easy to block, and the company is one more middleman. Tor helps but has its own problems. As Alex put it, both are workarounds on an internet that was never private by design. FIPS tries to fix the root: a permissionless internet, the same idea Bitcoin brought to money.

“You generate your identity yourself, instead of an IP address you have to request from your ISP.”

2A peer-observer case study with Razor

Learn Bitcoin Core by studying a real attack. peer-observer is a set of tools that watches the Bitcoin peer-to-peer network for attacks. There is no single starting point, so Razor’s advice is to start from real incidents and ask “how would we have spotted this?” This time: the 2026 address spam, written up on the Bitcoin Network Operations Collective forum (bnoc) as Address relay under stress.

First the basics. If nobody knows your node exists, nobody can connect to it. So nodes gossip about each other: you tell your peers “here I am” in an ADDR message, and they pass it on to their peers, and so on.

Mini-game 2 · Gossip✓ badge earned

Get D’s address all the way to A

Razor’s whiteboard: A, B, C and D sit in a line. D is new and only connected to C. Press the button to pass D’s ADDR message along.

Each node keeps a phone book of addresses (the boxes under each letter).

That phone book is addrman, the address manager in Bitcoin Core (src/addrman.h). It is simpler than a routing table: no paths, just a list of addresses you can try to connect to directly, plus who told you about each one. Here is what a few rows of a real dump look like:

Why peer-observer helps: Bitcoin Core only keeps today’s phone book. peer-observer dumps it every day, so you can see how it changed over months.

An ADDR (or the newer ADDRv2, which also fits Tor and other address types) can carry up to 10 addresses at once. Normally the average was about 2 per message. From around April 2026 it climbed to about 3.5. Small, but clearly not normal. Someone was spamming the network with bogus addresses that do not exist.

So why not test every address before you save it? Because honest nodes go offline. If your node crashes for an hour and everyone deletes you, you have to start gossiping from zero, and that is slow. Bitcoin Core needs forgiveness, so it keeps two tables.

Razor’s puzzle

More spam, but fewer new addresses?

Simplified sketch of the shapes from the bnoc post, not real numbers. You would expect a flood of fake addresses to push the second line up. Razor ended his talk right here: “I hope by the end of my talk you will also be confused.”

Spoiler: what the bnoc authors think is going on

The spam filled up the new table with fake entries that nodes could not easily throw away. With the table clogged, there was little room left for real new addresses, so fewer got added each day. A follow-up post discusses relaxing the rules for evicting old entries, and the tricky part: address gossip, unlike blocks or transactions, costs nothing to send, so spam is hard to price out.

3Floresta with stonepillar

Meet our newest fellow. stonepillar is a contributor to Floresta, a lightweight Bitcoin node written in Rust. It uses Utreexo to keep the data a node needs tiny, so you can validate your own transactions on a Raspberry Pi or even a phone instead of trusting someone else’s node. He will spend his three-month Code Orange fellowship on Floresta, and Floresta developers we met in Korea already speak highly of his work.

Working on Floresta is a great way to learn Bitcoin Core, because Floresta copies many of its parts. It even has its own address manager crate, the same idea Razor just explained. One recent fix stonepillar reviewed:

His main fellowship work: making Floresta’s RPCs (the commands apps use to talk to a node) behave like Bitcoin Core’s. There is a tracking issue full of RPCs still to build, and it is a good place for first-time contributors. His biggest piece so far is RPC authentication, which looks like “just check a password” until you read how Bitcoin Core does it:

Why it takes so many reviews

“Just a password check”, in layers

1Who can call at all: user and password, or a cookie file only the node’s own machine can read.
2What they can run: some commands move money or change settings, so access must be checked every time.
3What comes back: a sloppy answer can leak information or feed an app wrong data.
4Why it matters: a mistake here can end in lost funds, so security code gets extra eyes.

Key takeaways

  • Distributed beats decentralized for resilience. If one node going down can cut off a branch, there is still a choke point. FIPS aims for a true mesh where your npub is your address.
  • Learn Bitcoin Core through incidents. Address relay is just nodes gossiping “here I am” into a phone book. The 2026 spam shows why that phone book needs a forgiving “new” table, and why it can get clogged.
  • There is real work waiting for you. Floresta has a list of RPCs to build and PRs to review. Reviewing is how you start, and the people presenting on these calls are the ones learning the most.
